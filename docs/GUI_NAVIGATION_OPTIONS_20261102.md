# Issue #78：实空间 / 倒空间导航与窄窗口方案（待讨论）

本文件是设计审查，不是已实现的导航或布局改版。检查基线为 main
`f884b921f24444135a801014ff47a13d857f07ce`；本轮工程修复保持下述导航结构。
仅使用公开合成纹理。Windows 本地截图、完整网络记录及工作区未上传。

## P3：现有引用与边界

- `SavedViewHistory` 在浏览器内保存最多 40 个视图引用；`load()` 调用
  `remember()`，同网格的显示或标注修订可以替换当前历史项。返回/前进使用
  已保存对象 ID 调用既有 `show`，不会重算 FFT。它没有写入 owned Panel checkpoint，
  页面重新加载或新的浏览器会话会失去这条浏览序列。
- 启动时直接打开的空间视图标为“保存视图”，不是“原图”。这是有意保护：
  仅凭空间域和 frame ID，不能认定一个裁剪视图就是全帧显示配方。
- `frame_identity` 由服务端沿 `parent_object_id / base_object_id /
  source_object_id` 有界追溯到 `kind=frame`。它表达原科学帧，不表达“研究者希望
  回到哪条带观察标记、显示范围及标定版本的空间视图”。比较/来源不完整时可以为空。
- `SavedViewHistory.original()` 优先查找同帧、已明确标为“原图”或“全帧（新显示）”
  的历史项。没有时，使用同帧 ID 调用 `show {source_view:true}`。
  服务端限制该 ID 必须是当前 `frame_identity.frame_object_id`，然后按当前上下文
  新建全帧 preview。这不是恢复旧显示配方，也不会恢复原观察视图上的标记。
- “完整频谱”是恢复 FFT 自己的完整频域窗口；“全帧（新显示）”是上述空间源帧
  fallback。两个按钮的“完整/全帧”措辞接近，但行为不同。
- 晶体证据已包含 `source.observation_view_object_id`，观察侧栏可以调用既有
  `show` 返回它。没有晶体比较证据的普通 ROI→FFT 流程也需要自然的返回入口，
  不应把创建结构比较作为导航前提。
- owned checkpoint 已保留当前对象、frame identity、pending 引用、草稿与测量引用；
  保留当前对象不等于保留完整浏览历史或用户选择的空间观察视图。

## 本轮实测与分类

Windows Chrome 中实际执行：原图鼠标框选→保存观察→GUI FFT→“全帧（新显示）”
返回同一源帧的空间图像→“返回”依次恢复 FFT 和带观察的保存视图。没有重算 FFT
来实现导航。该会话内“返回”可用；fallback 的请求明确指向原 frame ID。

这不能重现 Issue #78 所述的所有入口。首次接收 FFT、重开 Panel 后仅有当前对象，
与同一会话已有空间历史是不同条件。“返回/前进 disabled”可以由历史为空解释，
不能单凭它认定历史按钮有确定性程序错误。没有发现足够证据支持本轮直接修导航。

| 分类 | 结论 |
| --- | --- |
| 确定性局部 bug | 本轮 GUI 路径未复现；仍需拿首次 FFT / 重开路径的确切对象链复核 |
| 交互说明 | “完整频谱”和“全帧（新显示）”容易混淆；原空间视图可能未被标为“原图” |
| 必要引用 | frame ID 足够回到科学源帧；不足以稳定恢复原观察视图及其旧配方；浏览历史未持久化 |
| 科学范围 | 返回图像不改变数值或解释资格；8 px 等周期差异不由导航结果解释为应变 |

## 三个最小方案

| 方案 | 改动与历史影响 | 来源、跨域与恢复 |
| --- | --- | --- |
| A：明确现有按钮语义 | 把“完整频谱”明确为“FFT 全域”，把源帧 fallback 明确为“查看空间源帧（新显示）”；已保存视图显示域和帧号。仍用当前历史 | 不新增引用；保留原 gate。能降低误操作，但重开后无法恢复原观察配方，不能独立解决 P3 |
| B：投影一个可验证的空间返回引用（推荐） | 从当前结果的既有不可变祖先链或已验证的 observation source，确定最近的适用空间保存视图；在 Panel state 暴露有界返回目标与依据，复用 `show`、`SavedViewHistory` 和现有 pending 接纳 | 验证目标确属对应 frame/ROI；明确“原观察保存版本”和“源帧新显示”的区别。跨域必须保留草稿保护并明确切换。重开时重读验证既有引用，失败则禁用并说明，保留当前科学对象 |
| C：持久化现有 SavedViewHistory | 在同一 owned checkpoint 增加有界 ID/role/frame 列表和游标；已接纳的 Agent 视图与 GUI 视图进入同一历史 | 不另建工作区。恢复时逐项检查对象存在、帧和角色；无效项显式标为不可用。能恢复来回浏览，但新增 checkpoint 兼容与截断/分叉语义，单独实施成本高于 B |

建议先讨论 **B + A 的必要文案**。保留 C 作为之后的会话恢复增强。B 的目标选择
不能靠文件名、频域图像外观或“同一个文件”推断；也不能把空间数组 ID 冒充已保存
PNG 视图。没有合格的保存引用时，继续使用现有源帧 fallback 并明确这是新显示。

B 的显示信息应至少区分：当前域、当前 frame、可返回的保存观察视图/源帧、目标
标定版本。打开旧视图恢复它自己的标定和显示，不能静默套用当前新标定后仍称“原图”。
此处只建议在现有 Panel state/checkpoint 中投影/保留引用，不创建另一套导航系统。

后续验收至少包含：GUI-first、首次 Agent FFT、浏览器刷新、正常关闭重开、标定已
修订、目标引用缺失、比较包含多个 frame、存在新草稿、旧结果晚到。每条返回均核对
原图/FFT/测量对象与数组哈希，确认只是查看保存对象或明确的新显示，没有重算 FFT。

## P4：760×800 的真实空间分配

现有布局不是完全缺少抽屉。宽窗口的观察侧栏为 360 px，中间断点为 320 px；
`max-width:850px` 时取消画布右 margin，观察侧栏变成 340 px 覆盖层。
属性侧栏也已有窄屏覆盖规则。底部结果工作区与画布共享纵向高度预算。

在本轮 **760×800 CSS viewport** 中，实测：

- 左工具栏后画布 viewport 宽 704 px。
- 打开的观察抽屉为 x=420、y=62、width=340、height=738；它覆盖科研操作条和导航
  条的右侧，并非只覆盖图像。保存当前 ROI 按钮右缘约 x=450，落在抽屉覆盖区内。
- 从宽窗口缩小后，图像原有相机位置仍在 x≈435，原宽度约 713 px；抽屉开启时
  可见图像很少。收起抽屉并点“适应画布”后，原 ROI 与图像仍在，可继续操作。
- 因而需分别处理覆盖范围、操作可达性、相机可见范围，不能把它们统称为“侧栏挤压”。

| 方案 | 收益与代价 |
| --- | --- |
| 1：收敛现有抽屉（推荐先讨论） | 窄屏只保留一个观察/属性抽屉；关闭入口固定可达。明确覆盖模式，关键保存与返回操作放入当前可见区域或抽屉内部；顶部辅助操作进入有标识的溢出菜单。适应画布使用实际未遮挡区域，保留手动相机状态并提供显式恢复，不静默移动科学选区 |
| 2：宽屏可调侧栏，窄屏沿用受限抽屉 | 宽屏允许调整宽度并设置最小画布宽度；不足时切换到方案 1 的抽屉。科研长说明更灵活，但增加拖动、键盘可达、尺寸恢复及断点联动测试，暂不作为第一步 |

本轮没有实施上述方案，也没有全局美化。Kimi-K3.1 可据此独立审查人的操作顺序、
状态可读性和视觉层级。相机调整只影响展示；任何布局提案均须保留当前 ROI、草稿、
历史对象和三层科学结果语义。
